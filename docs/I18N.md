# Multi-language support

Status board and design notes for making AmoledOS speak more than one language.

Note on languages: the project's **comments and documentation are in English**,
but the **source language of the user interface is Spanish** — the catalogue key
is the Spanish string itself, gettext style. Those are two different things and
the rest of this document is about the second.

## Decisions

| Question | Answer |
| --- | --- |
| Source language | **Spanish, in the code.** English is a translation, not the other way round. Nothing gets rewritten - strings get wrapped. |
| Catalog key | **The Spanish string itself**, gettext style. No invented identifiers. |
| Where packs live | **microSD, under `/lang/`.** Added without reflashing. |
| Fallback | No pack loaded means `aos_tr()` returns its own argument, so the system behaves exactly as it did before. No card means Spanish, which is the source language anyway. |

Using the msgid as the key means a changed Spanish string silently orphans its
translation. That is the accepted cost: `tools/gen_lang.py` (phase 0) will
diff catalogs against the sources and report orphans.

## F1 - the font set (done)

### The problem

LVGL's Montserrat is generated with `-r 0x20-0x7F,0xB0,0x2022`. That is pure
ASCII: no accented vowels, no n-tilde, no inverted question mark. When a glyph
is missing LVGL draws **nothing** - no error, no log, no replacement box - so
the defect is invisible until someone reads the screen carefully.
`aos_app_settings.c` had been shipping "Tocá el centro de la cruz" with a hole
in it.

### What was done

- `tools/gen_fonts.py` generates `components/aos_fonts/aos_montserrat_{14,16,20,28,36,48}.c`
  with `0x20-0x7F,0xA0-0xFF,0x2022,0x20AC` plus the 61 FontAwesome codepoints
  behind the `LV_SYMBOL_*` macros. 254 glyphs per size, up from 158.
- `aos_theme.c:pick()` now returns these fonts. The `#if LV_FONT_MONTSERRAT_*`
  guards are gone: they existed because the built-in set differed between the
  simulator (`lv_conf.h`) and the board (Kconfig), and ours are always present.
- The simulator compiles the same sources, so it renders accents identically.
- `tools/gen_symbols.py` gained `aos_fonts` in `DEFAULT_LIBS`, so the six new
  fonts reach the dynamic apps. **This is easy to miss**: a new component's
  archive is not picked up automatically, and the first run after adding one
  reported the same 2398 symbols as before, silently.
- `aos_day_name()` now returns `MIÉ` and `SÁB`, which is how those abbreviations
  are actually spelled. They render three characters wide as before; UTF-8 makes
  the C string one byte longer, not the drawn text.

### The stock fonts stay compiled in (until F7 - see below)

Turning off `CONFIG_LV_FONT_MONTSERRAT_*` would drop those symbols from the
dynamic-app symbol table, and the four apps that name `lv_font_montserrat_*`
directly (flappy, arkanos, g2043, hello_app) would fail to load. Both sets are
compiled for now. Migrate those four to the `aos_font_*` role pointers, then
delete the duplicate. *(Done in F5 and F7 respectively.)*

### Cost, from the linker map

| | Glyphs | Flash |
| --- | ---: | ---: |
| `lv_font_montserrat_*`, six sizes | 158 | 237.1 KB |
| `aos_montserrat_*`, six sizes | 254 | 352.3 KB |
| **Extended range costs** | +96 | **+115.2 KB** |

Carrying both sets during the transition puts the binary at 2.45 MB, 51 % of
the 5 MB partition free. F7 dropped the stock set: 2.22 MB, 56 % free.

Adding Latin Extended-A (`0x100-0x17F`: Polish, Czech, Slovak, Turkish,
Croatian, Hungarian, Romanian) would take the bitmap arrays from +102 KB to
+254 KB over ASCII - roughly +280 KB compiled, more than twice this range.
Montserrat covers the block completely, so it is one string in `gen_fonts.py`
plus a rebuild, but it is not free: those glyphs are as wide as the letters
they decorate.

> Measuring gotcha: counting `0x[0-9a-f]{2}` in the generated `.c` undercounts
> the bitmap array by about half, because `lv_font_conv` does not zero-pad and
> emits `0x5,` as readily as `0xab,`. An early estimate of "+44 KB" came from
> exactly that mistake. Read the linker map instead.

### Requirements

```
brew install node
npm install -g lv_font_conv
```

`Montserrat-Medium.ttf` and `FontAwesome5-Solid+Brands+Regular.woff` are
already in the repo under `sim/lvgl/scripts/built_in_font/`.

### Regenerating

```
python3 tools/gen_fonts.py     # rewrites components/aos_fonts/
idf.py build
python3 tools/gen_symbols.py   # only needed if SIZES changed
idf.py build
```

### Verified

- All six sizes carry 254 glyphs; every one has bitmap data except U+00A0, the
  non-breaking space, which correctly has none.
- Firmware builds, 51 % of the app partition free.
- Simulator builds and renders `SÁB 5 SEP` on the watch face with the accent
  drawn correctly; FontAwesome symbols still render.
- `tools/build_apps.sh`: all 19 apps build, ABI 2, every undefined symbol
  resolves against the regenerated table.

Not verified on hardware - no board run yet.

## F0 - the plumbing (done)

Verified in the simulator, not on hardware.

### What exists now

- `components/aos_ui/aos_i18n.{c,h}` - `aos_tr()`, the `_()` macro, catalog
  loading, the pack scanner, and the language switch.
- `aos_hal_path_lang()` on both HALs. **SD only**, unlike every other
  `aos_hal_path_*`, which fall back to SPIFFS. No card means the directory does
  not exist, `opendir()` fails, and the system runs in Spanish - which is what
  the source says anyway. The fallback costs no code.
- `tools/gen_lang.py` - extracts, writes templates, and diffs a pack against
  the sources.
- A Settings dropdown under `IDIOMA`, and `aos_ui_request_language()` to apply
  the change on the next tick.
- `t` in the simulator rotates through the installed packs, through the same
  deferred path as the dropdown.

`aos_tr` and the whole `aos_i18n_*` API are in the symbol table (2404 -> 2415
symbols) so the dynamic apps can call them in F4. `AOS_ABI_VERSION` is
untouched at 2 and every existing `.so` still loads.

### It lives in aos_ui, not in its own component

Deliberate. The dynamic apps already see `aos_ui/include`, `aos_ui` is already
in `gen_symbols.py`'s `DEFAULT_LIBS`, and the simulator already globs
`components/aos_ui/*.c`. A new component would have needed all three wired up
by hand - and F1 already showed what happens when one of them is missed: the
symbol generator reported the same count as before and said nothing.

### Layout

A pack is a directory you copy to the card:

```
/sdcard/lang/
└── en/
    ├── meta.txt          name=English, format=1
    ├── _sistema.lang     the firmware's strings + every app NAME
    ├── demo.2043.lang    one catalog per app, named after aos_app_desc_t.id
    └── aos.clima.lang
```

Catalogs are keyed by `desc.id` and not by the `.so` filename, so the same
mechanism covers built-in and dynamic apps and there is no second naming
scheme to keep in sync.

App names live in `_sistema.lang`. They have to: the launcher draws "Gemas"
without having opened Gemas, so that app's catalog is not loaded. The launcher
calls `_(app->desc.name)` when it draws, which means **no app - built-in or
dynamic - needs any change to have its name translated**.

### File format

Tab-separated, one pair per line, `#` for comments:

```
# amoledos-lang 1   es -> en
Sin conexion	No connection
Ene\nFeb\nMar	Jan\nFeb\nMar
```

**The escaping is load-bearing.** In C, `_("Ene\nFeb")` hands `aos_tr()` a
string with a real newline - the compiler resolved the escape. A line-oriented
file cannot carry one, so the catalog stores the escaped form and `unescape()`
undoes it before hashing. `gen_lang.py` writes keys exactly as they appear
between the quotes in the source, which is the other half of the same
agreement. Break either half and the 24 multi-line strings miss every lookup
in silence.

### Lookup

The file is read whole into PSRAM, unescaped in place (it only ever shrinks),
and indexed by an array of `{hash, key offset, value offset}` sorted by hash.
FNV-1a, binary search, `strcmp` on a hash hit. Collisions are handled by
walking both ways over equal hashes, because `qsort` gives no order among
equal keys.

`aos_tr()` returns its argument immediately when nothing is loaded - the
common case does not even hash.

### Switching language

`aos_i18n_set()` builds the new catalog **before** freeing the old one, so a
half-readable pack cannot leave the UI with no strings at all.

The switch is deferred to `aos_ui_tick()` via `aos_ui_request_language()`,
because applying it inside the dropdown's own callback would free the very
strings the visible screen is built from - the same reason the watch-face
picker is deferred.

`apply_language()` goes home and then calls `destroy_all_app_instances()`,
which tears down **background** apps too. Two reasons: their LVGL labels hold
text already copied in the old language, and if an app had stashed a pointer
returned by `aos_tr()` in its own state, that pointer is about to dangle.
Killing a running timer is a real cost, but changing language is rare and
deliberate.

### Verified

- Launcher renders in English from a pack and back, both from a saved
  preference at boot and switched live at runtime.
- `es -> en -> es` round trip with catalogs loaded and freed, no crash.
- Firmware builds, 51 % of the app partition free. All 19 apps rebuild, ABI 2,
  every symbol resolves.

### Gotchas found while building it

- **`gen_lang.py` was extracting `_()` out of comments.** Its first run pulled
  the `_("Ene\nFeb")` example out of `aos_i18n.c`'s own documentation and filed
  it as a UI string. A phantom catalog entry is invisible - it translates
  nothing and never fires. The extractor now blanks comments first, keeping
  byte offsets so `file:line` stays honest, and tracks string literals so the
  `//` in `"http://"` does not eat the line.
- **`-Werror=format-truncation` fires on the board but not on macOS.**
  `read_meta_name()` copied a 122-byte line into a 28-byte field. `meta.txt`
  comes off the card, so it is external input: the bound is now written out as
  `"%.*s"` rather than left to `snprintf` to apply silently.
- **Watch where an include lands.** `#include "aos_i18n.h"` went inside the
  `#ifndef AOS_SIM` block in `aos_app_settings.c` and only the simulator
  noticed.

## F2 - marking the firmware (done)

All 27 files of `components/aos_ui` and `components/aos_apps`. **353 keys,
312 `_()` call sites, 347 translated** - the remaining six are proper nouns
(ARKANOS, Claudito, Flappy, 2043, Simon, Pomodoro), and another 71 entries are
deliberately identical in both languages: city names, SI-adjacent units, and
words like "Reset" and "MENU".

Three mechanisms had to be added along the way. None of them were in the F0
design, and all three came out of real strings rather than speculation.

### N_() - mark here, translate there

`aos_tr()` is a function call, so it cannot appear in a static initializer.
Tables like the 40 cities in the world clock or the 80 units in the converter
have to store Spanish and translate where they are drawn:

```c
static const city_t CITIES[] = { { N_("Nueva York"), "EST5EDT,M3.2.0,M11.1.0" }, ... };
...
aos_label(row, _(CITIES[i].name), ...);
```

`N_` expands to nothing; it exists so the extractor can see the string.
**Always in pairs.** `N_` alone puts a key in the catalog that nothing looks
up; `_` alone on a table entry does not compile, which at least tells you.

Only the left half is marked in the city table. The right half is a POSIX TZ
rule that `setenv("TZ")` consumes - configuration, not text. Same in the
converter: unit *names* are marked, unit *symbols* (mm, kB, m/s) are not,
because SI notation is the same everywhere and translating it would only
invite mistakes.

### C_() - when one Spanish word is two things

"MAR" is both *martes* and *marzo*. English wants TUE for one and MAR for the
other, and a key that is the Spanish string cannot serve both. The context is
glued to the key with a 0x04 byte, gettext's own convention:

```
dia\x04MAR	TUE
mes\x04MAR	MAR
```

`C_("dia", s)` at the draw site, `NC_("dia", "MAR")` in the table. The catalog
stays plain ASCII because the separator is written as the escape `\x04` and
`unescape()` turns it back into the byte.

With no match, `aos_trc()` returns the Spanish rather than falling back to the
plain key: a bare "MAR" in the catalog is by definition the *other* meaning,
and the wrong month is worse than Spanish.

### AOS_I18N_MARK=1 - see what is still Spanish

Prefixes every string that reached `aos_tr()` and came back without a
translation, so one glance at a screen says what is left.

Read the limits, because they matter: it catches a **key that is not in the
catalog** - not written yet, or not matching what the extractor filed. It does
**not** catch a string drawn from a site nobody wrapped, because then no call
happens at all. For that class, look at the screen.

### The LV_SYMBOL trap

```c
snprintf(buf, n, _(LV_SYMBOL_WIFI "  conectando..."));   /* WRONG */
```

The preprocessor pastes the glyph's bytes onto the front, so `aos_tr()` looks
up "\xEF\x87\xAB  conectando..." while `gen_lang.py`, reading the source,
files "  conectando...". They never meet, nothing errors, the string stays
Spanish forever. Pass the symbol as an argument instead:

```c
snprintf(buf, n, LV_SYMBOL_WIFI "  %s", _("conectando..."));
```

`gen_lang.py` now warns about any `_()` holding a literal glued to an
identifier, which is exactly this shape and only this shape - `C_("dia",
days[i])` is a literal beside other arguments and stays quiet.

### The bug the tools could not see

The converter's unit names were marked with `N_`, were in the catalog, had
English translations - and still drew in Spanish, because three
`lv_label_set_text()` calls on the main screen were never wrapped. The
extractor was happy. The marker could not fire. Only the screenshot showed it.

That is the shape of most of what is left in F2 and F4: not missing
translations, but draw sites nobody wrapped. Budget for looking at every
screen, which is what F5 is.

### Spanish orthography that was living in the code

The calendar footer lowercased the first letter of the weekday with

```c
dia[0] = (char)(dia[0] - 'A' + 'a');
```

That is the Spanish rule - *sábado 5 de septiembre* - written as byte
arithmetic, and it made the English build say "saturday 5 september". The fix
is a second table in lowercase, `DIA_LARGO_MIN`, which mirrors what the file
already did for months with `MES_CORTO_MIN`: let the catalog decide the
spelling instead of the code.

Worth looking for elsewhere. Anything that manipulates letters positionally -
casing, truncation, pluralising by appending "s" - is a language rule in
disguise.

### What stays unmarked, on purpose

A sweep of every visible literal not covered by a marker came back with 97,
and all 97 are correct:

- **POSIX TZ rules** in the world clock (`PST8PDT,M3.2.0,M11.1.0`). `setenv()`
  eats these; translating them breaks the clock.
- **Unit symbols** in the converter (mm, kB, m/s, hPa). SI notation is the
  same everywhere.
- **Format-only strings** with no words: `"%.3f V\n%+.0f mA\n%.1f C"`.
- **`aos_hal_board_name()`** - hardware identity, like a model number.
- **`desc.name`** values, which the extractor collects separately and the
  launcher translates at draw time.
- Log messages, preference keys, and LVGL filesystem paths.

### Verified

- Settings, world clock, converter, calendar, pomodoro, battery and BT control
  all render in English with `AOS_I18N_MARK=1` and no marks left on screen.
- The world clock's times are still right - the TZ rules were left alone.
- The calendar header reads `M T W T F S S`, which is the context mechanism
  resolving the two Spanish `M`s, and the watch face reads `SAT 5 SEP`.
- Spanish still reads `Hoy: sábado 5 de septiembre` - with the accent it could
  not draw before F1.
- Firmware builds, 51 % of the app partition free. 19/19 apps rebuild.

## F4 - the dynamic apps (done)

All 19 apps. **18 catalogs, 378 app keys** on top of the firmware's 355, for
**733 in total**. `truco` is the one app with no catalog, and that is the point:
its calls - *envido*, *quiero retruco* - are the names of the plays, not
interface copy, and a translated truco is no longer truco. The file says so at
the top.

No new infrastructure was needed - `aos_tr` was already in the symbol table
and each app just includes `aos_i18n.h`, which `apps/common.cmake` already
puts on the include path. `hello_app` went first as a two-minute smoke test to
confirm `aos_tr` really does resolve as an undefined symbol at load time
before touching anything large.

### The apps draw text with fonts aos_fonts never sees

This is the difference between F2 and F4, and it is not small. Three of these
apps render into their own pixel buffer with their own bitmap font:

| App | Font | Range |
| --- | --- | --- |
| g2043 | `gx_text()`, 5x7 | ASCII 0x20-0x5F, **uppercase only** (lowercase is folded up) |
| arkanos | `ak_text()`, 5x7 | same shape |
| claudito | `cl_text()`, 5x7 | ASCII 32-126, no accents |

Out-of-range bytes are silently skipped, exactly like the LVGL font before F1 -
but the Latin-1 work does nothing for these, because they are not LVGL fonts.
**Any translation of in-canvas text has to stay inside that app's charset.**

Two more traps in the same place:

- `gx_text_w()` and friends measure with `strlen`, so a multi-byte UTF-8
  character counts as two and centring goes wrong even if the glyph existed.
- Several of these strings land in fixed buffers: `ak_popup()` copies into a
  `char txt[8]` (seven usable characters, truncated in silence) and claudito's
  speech bubbles are `char[20]`. The catalogs carry comments saying so.

`ak_draw.c` also had `for (i = 0; i < sizeof(pausa); i++) buf[i] = pausa[i];`
over a `char buf[16]` - fine for a literal the compiler sized, an overflow the
moment the string comes from a catalog. Rewritten as a bounded copy.

### Spanish grammar in the code, again

`atasco` built its plural by appending a letter:

```c
snprintf(buf, n, "Nivel %d completado en %d movimiento%s",
         level, moves, moves == 1 ? "" : "s");
```

Now two complete sentences, one per form, so the translator gets whole phrases
instead of a stem and a suffix. English happens to pluralise the same way;
plenty of languages do not.

### Translating the data, not just the strings

`clima` asked open-meteo for city names with `&language=es` hard-coded. It now
sends `aos_i18n_current()`, so with the UI in English searching for "Londres"
finds "London". That is not a catalog lookup - it is the app asking the server
for the right language - and it is the kind of thing that only shows up when
an app talks to the outside world.

### The first real layout casualty

2043's option chips are absolutely positioned with fixed widths. "AUTO NO" fit
in 76 px; "AUTO OFF" spilled off the left edge of the screen. Re-laid the row
around the longest label in *any* language (88+68+68+100 with 6 px gaps and 13
px margins) rather than around the Spanish.

Absolutely-positioned fixed-width rows are where F5 will spend its time.
arkanos, clima and claudito came through untouched.

### Verified

- The four biggest apps render in English with `AOS_I18N_MARK=1` and no marks
  left on screen; the per-app catalogs load on open (48, 51, 52 and 36
  strings).
- Spanish is unchanged, checked side by side on 2043.
- 19/19 apps build, ABI 2. Firmware 51 % free.

### The tooling learned two things

- **`gen_lang.py` silently skipped remoto's whole catalog.** It writes its id
  as `#define APP_ID "aos.remoto"` and assigns the macro, which the extractor
  could not read - it warned and moved on, quietly losing 41 strings. It now
  resolves that indirection.
- Marking a table with `N_` whose draw site does not exist leaves an orphan
  key. claudito's food names were marked before noticing nothing ever draws
  them; the marks came back off. **`N_` without a matching `_` is a defect,
  not a spare.**

### The sweep that lied, and the one that replaced it

Two of the three verification tools missed things, and it is worth writing
down exactly how.

**A substring where a word was meant.** The manual sweep for "visible literals
nobody marked" excluded lines matching `printf` - and `printf` is a substring
of `snprintf`. Every `snprintf` line in the project was invisible to it. That
sweep is what produced the confident "97 literals, all 97 correct" at the end
of F2. Redone with word boundaries it found **23 real misses**, including
`sensores`, an entire app that had been declared to have nothing to translate.

**A char literal that ate a file.** `strip_comments` handled `'x'` but left
the quote inside `'"'` - normal in any JSON parser - which made the
string-literal regex swallow hundreds of lines as one "string". It now blanks
char-literal bodies.

Both are now `python3 tools/gen_lang.py unmarked`, which exits non-zero when
it finds Spanish-looking text that no marker covers. It is the third leg
alongside `check` (catalog vs code) and `AOS_I18N_MARK` (runtime), and it is
the only one that can see a string nobody wrapped:

| Tool | Sees |
| --- | --- |
| `check` | keys in the catalog that the code lost, and code keys the catalog lacks |
| `AOS_I18N_MARK=1` | wrapped strings with no translation |
| `unmarked` | **UI text that was never wrapped at all** |

Two entries survive it and are correct: a continuation line of an
`aos_hal_log()` call, and a hostname format string.

### N_ without its _ , four more times

`escaner`'s `fase_txt()` returned the marked table unwrapped, so the scan
status stayed Spanish with no marker to show it. `cotiz` drew
`esp->nombre` raw. Both were found by looking at the screen, not by a tool.

A per-file check of "N_ marks with no `_(expr)` call" gives too many false
positives to be useful - the marker and the draw site are usually in different
files, which is the whole point of the pair. The reliable check remains: open
the app in the other language and read it.

## F5 - layout QA (done)

37 screens in both languages. **No layout regression from the English
translation** beyond the 2043 chip already fixed in F4.

### Audited, not eyeballed

80 screenshots would have answered the question once and been worthless for
the third language. `tools/audit_layout.sh` opens every screen in every
installed language, walks the LVGL tree and reports three things:

| | |
| --- | --- |
| `CORTADO` | the text does not fit its own box - a fixed width sized for Spanish |
| `AFUERA` | the label leaves the 368x448 screen |
| `DESBORDA` | the label leaves its container |

**What matters is the difference between languages, not the total.** A finding
present in both is a pre-existing condition; only one that appears in a
translation is a regression. The script separates the two and exits non-zero
on regressions.

Two thresholds had to be tuned before the output was worth reading, and both
are written down in `sim/main.c` so nobody re-derives them:

- `lv_text_get_size()` returns the full line height including the descender,
  about 3 px more than the box even when the text fits. Compare with `+4`.
- LVGL areas are inclusive but `lv_obj_get_transformed_area()` adds a pixel of
  margin: a full-width label reports `0..368`, not `0..367`. Compare with `>`,
  not `>=`.

It also skips hidden objects - the tuner's noise tab was reporting text at
y=478 on a 448-tall screen while being perfectly invisible - and it does not
treat vertical overflow inside a scrollable page as a problem.

### What it found that eyes had not

The tuner's own page is `AOS_SCREEN_H - 30 - 42 = 376` px tall and its content
ran to 426. The TONE button was cut off by the screen edge and the hint below
it - *escuchar y sonar no van juntos* - **was never visible at all**, in either
language, since before any of this work. Everything below the needle moved up
about 30 px.

Three more were cosmetic and now fixed: two labels whose box was 30 px tall
under a font with a 35 px line height (the tuner's octave, remoto's title -
neither had visible descenders, so nothing looked wrong), and a sensor status
line ending 2 px below the screen.

The audit is now clean: 37 screens, two languages, zero findings. That is the
baseline the next language gets compared against.

### What it still cannot see

Overlap, ugliness, and a string nobody wrapped. The three tools each see a
different slice and none of them sees everything:

| Tool | Sees |
| --- | --- |
| `gen_lang.py check` | catalog vs code |
| `gen_lang.py unmarked` | UI text never wrapped |
| `AOS_I18N_MARK=1` | wrapped text with no translation |
| `audit_layout.sh` | text that does not fit |

### Not everything on screen comes from a catalog

`remoto` draws its buttons from the user's own JSON profile - *Techo*,
*Velador*, *Cortina*. Those stay in whatever language the user typed, and
should: they are that person's data, not our copy. Same for city names typed
into `clima` and for recording filenames. Worth remembering before someone
files it as a missing translation.

## On hardware (2026-09-05)

Everything up to here had been verified in the simulator only. Flashed to the
board - ESP32-S3, 8 MB PSRAM, revision v2 (CO5300 + CST816) - and the whole
chain works:

- **19 dynamic apps load.** This was the one real risk: every `_()` inside a
  `.so` is a literal in `.rodata` plus a pointer, the shape that used to crash
  the ELF loader through `.data.rel.ro`. All 19 register cleanly.
- The English pack uploads over Wi-Fi, 20 files, 55 KB.
- Switching language from the browser works and the UI survives it.
- The choice persists: after a reset the log says `idioma: en, 355 cadenas`
  before the apps even load.

One warning on the console is a red herring worth writing down: the Waveshare
BSP prints *"Long filenames on SD card are disabled in menuconfig!"* on every
boot. They are not - `CONFIG_FATFS_LFN_HEAP=y` with `MAX_LFN=255` has been set
since the `.so` files needed it. The BSP just does not look at our config. If
it were true, `demo.claudito.lang` could not exist.

## The .so files on the card are a separate artifact

Reported from the board, and worth writing down because the symptom points
away from the cause: **the firmware and its built-in apps showed English while
every dynamic app stayed Spanish.**

Nothing was wrong with the translation. `tools/build_apps.sh` compiles the
`.so` files into `apps/<x>/build/` and says "ready to copy to /sdcard/apps/" -
it does not install them. The card still held the binaries from before F4, so
those apps had no `_()` calls in them at all. `claudito.so` was 33252 bytes on
the card against 34492 freshly built.

There are now two install steps and both go over Wi-Fi:

```
./tools/build_apps.sh                      # compile
./tools/install_apps.sh 192.168.1.116      # upload + reset the board
./tools/install_lang.sh 192.168.1.116 en   # upload the packs
```

`install_apps.sh` resets the board when it finishes: the firmware loads every
`.so` once at boot, so without a reset nothing changes and it looks like the
upload failed. `build_apps.sh` now says all this at the end instead of the old
"ready to copy".

A detail that reads like a bug and is not: the boot log registers apps by
their compiled `desc.name` - *Claudito*, *Cotizaciones* - even in English,
because the launcher translates at draw time. The log shows the raw name; the
screen shows the translated one.

## Uploading a pack

The portal already had a file manager - `/api/upload`, `/api/list`,
`/api/delete` - over a whitelist of directories in `resolve_dir()`. Adding
`lang` and `lang/<code>` to that whitelist made all three work on packs
without a new handler. The language code is validated by hand (letters,
digits, dash, underscore) because it arrives from the network and `lang/../..`
would otherwise walk out of the tree; `upload` mkdirs `/lang` and
`/lang/<code>` on the first file.

```
./tools/install_lang.sh 192.168.1.116 en
```

Twenty files over Wi-Fi, no card removal. Then either pick the language on the
watch, or from the same browser:

```
curl http://<board>/api/lang                       # what is installed
curl -X POST http://<board>/api/lang -d code=en    # switch
```

`POST /api/lang` does **not** call `aos_i18n_set()`. It runs on the HTTP
server's task and switching language destroys LVGL objects, so it calls
`aos_ui_request_language()` and lets `aos_ui_tick()` apply it - the same
deferred path the Settings dropdown uses. That is the reason the request/apply
split exists.

## Pseudolocalisation

English was a weak test: it is **shorter** than Spanish, so the layout audit
never had to catch anything. `gen_lang.py pseudo` generates an `xx` pack from
the Spanish keys instead of a translation:

```
Ajustes            ->  [Ájüstés···]
Hoy: %s %d de %s   ->  [Hóý: %s %d dé %s··]
```

Three things at once. **Brackets** so a truncation is obvious - if the `]` is
missing, the string did not fit. **Accents** on every screen, which tests the
Latin-1 font against real text everywhere rather than wherever a real language
happens to need one. **Padding proportional to the letter count** (+40 % by
default), because the point is the maximum length, not the length some
language happens to have.

Format specifiers and escapes are preserved exactly - `%02d`, `%+.2f`, `\n`,
`\x04` - or `snprintf` would break. A check confirmed 733/733 came through
untouched.

`demo.2043`, `demo.arkanos` and `demo.claudito` are expanded **without**
accents: those three draw with their own ASCII bitmap fonts, so an accent
there is noise rather than signal.

### What it found that English did not

Seven layout weaknesses on the first run, all real:

- **The calendar header.** A long month name pushed the year out of the row
  and both spilled out of the header. Now the month has a fixed width and
  ellipsises.
- **Settings' memory diagnostic** grew past both screen edges. Now bounded and
  wrapping.
- **Simon's centre label** had a box one line tall, so a longer word wrapped
  and the second line was cut. The circle is 112 px; the box is 68 now.
- **The chips in 2043 and arkanos.** Absolutely positioned, fixed width, four
  across 368 px - there is no room to grow. The labels now clip to their own
  chip with an ellipsis: ugly but contained, instead of drawing over the
  neighbour.

And one that was not a layout bug at all:

### The four apps still on LVGL's ASCII font

The padding character rendered as empty boxes in 2043 - but fine in the
calendar. The calendar uses `aos_font_*`; 2043 was still calling
`&lv_font_montserrat_16` directly, and **those fonts have no accented glyphs
at all**. F1 left this as a note - "migrate those four, then delete the
duplicate" - and English never exposed it because English needs no accents.

32 references across arkanos, g2043, flappy and hello_app now point at
`aos_montserrat_*`, which the symbol table already exported;
`apps/common.cmake` gained `aos_fonts/include`. The 266 KB of LVGL's own
Montserrat can come out of the build whenever someone wants the flash back -
which is F7.

### Two corrections to the audit itself

- **It only compared horizontally.** The calendar label that wrapped to two
  lines fitted across and spilled *down* out of its header. A screenshot found
  it; the tool did not. It now checks both axes, with the same
  scrolling-parent exemption the screen-bounds check already had.
- **`LV_LABEL_LONG_MODE_DOTS` is not a failure.** It is the screen's author
  saying "clip this if it does not fit". Those are reported separately as
  `PUNTOS`, listed under "check the translation still reads", and do not count
  as regressions.

Clean afterwards: 37 screens x 3 languages (es, en, xx), zero findings.

## German - the third language

733 keys. Chosen over Portuguese because it is the longest Latin-script
language likely to be wanted: *Ajustes* becomes *Einstellungen*, *Remoto*
becomes *Fernbedienung*, *Nivel* becomes *Wasserwaage*. If the layout survives
German it survives most of Latin script.

Written by Claude, correct but not native. Fine as a tooling test; have a
speaker read it before anyone ships it.

### Transliteration where the font cannot follow

`demo.2043`, `demo.arkanos` and `demo.claudito` draw with their own bitmap
fonts and have no umlauts, so their catalogs are transliterated: *DANKE FUERS
SPIELEN*, *ZURUECK ZUR UHR*, *ZWOELF MAUERN UND EIN BALL*. Everything drawn by
LVGL keeps its ä ö ü ß.

`gen_lang.py check` now enforces this. It flags **non-ASCII only** in those
three catalogs, and that precision is the point:

- `gx_text()` and `ak_text()` **fold lowercase to uppercase**, so a-z renders
  fine even though the glyph table starts at 0x20. A first version flagged
  every lowercase letter and was pure noise.
- The catalog cannot know which string goes to the canvas and which to an LVGL
  label - both live in these apps. An accent is the only character that fails
  down *either* path, so it is the only thing that can be asserted without
  reading the code.

The pseudolocalisation padding had the same problem: `·` is Latin-1, which
those fonts do not have. `PSEUDO_PAD_ASCII` is a plain `.` for them.

### What German broke

One thing: cotiz's footer wrapped to two lines in a box sized for one -
*tippen zum Aktualisieren - wählen unter /cotiz* is simply longer than the
Spanish. The box is 42 px now.

That is the whole list, and it is a good result: the pseudolocalisation had
already found and fixed the structural weaknesses at +40 %, so a real language
at +20 % had almost nothing left to hit. **Running the pseudo pack first was
worth it.**

### Three more holes in the audit, found by German

Each was found by looking at a screen the tool had called clean.

1. **The menu has three styles and only one shows names.** `AOS_SIM_VIEW=launcher`
   uses whatever style is saved - honeycomb here, which has no text at all. The
   screen where a long app name gets cut was never audited. `grid` and
   `honeycomb` are in the list now.

2. **The "fixed width" filter hid the labels that matter.** The `CORTADO` check
   only looked at labels whose *style* width was not `LV_SIZE_CONTENT`, which
   excludes every label sized by its parent's layout - exactly the launcher's.
   The filter was also unnecessary: a content-sized label's width equals its
   natural width, so it can never trip the comparison anyway.

3. **`LV_LABEL_LONG_DOT` overwrites the label's own text.** After LVGL
   ellipsises, `lv_label_get_text()` returns `"Taschenla..."`, not
   `"Taschenlampe"` - so measuring the text measures the *truncated* string,
   which of course fits. Truncation there cannot be measured, only inferred:
   dots mode, text ending in `...`, and a width that reaches the box edge. The
   edge condition is what separates it from a string that legitimately ends in
   dots, like *Buscando...* in a roomy box.

With those three fixed the audit reports what it should: four German app names
ellipsised in the launcher - and **two Spanish ones that always were**,
*Temporizador* and *Reloj mundial*, correctly filed as pre-existing rather than
as a German regression.

Only *Taschenlampe* was shortened, to *Lampe*. *Fernbedienung*, *Wasserwaage*
and *Minesweeper* keep the correct word and ellipsise, which is what the
launcher was designed to do.

### Final state

39 screens x 4 languages (es, en, de, xx), zero findings.

## F6 - English inside the firmware (done)

English used to live only on the card. Now the firmware ships with it built
in, and the card carries the third language onward. A watch with no microSD
at all offers Spanish and English.

**Embed it in the binary, not in SPIFFS.** SPIFFS would need a second flash
step and a second artifact that can drift out of sync with the code - and
version skew is exactly what msgid-as-key is most vulnerable to, because a
changed Spanish string silently orphans its translation. Embedded in the
firmware image, the catalog and the code that keys into it ship together and
cannot disagree.

The loader barely changes: `catalog_parse()` already works on a blob rather
than a file. The embedded path just copies the const blob into a mutable
buffer - `unescape()` writes in place - instead of `slurp()`ing.

**Search order: card first, then embedded.**

1. `/sdcard/lang/<code>/` — a pack on the card wins
2. the embedded catalogs — English
3. nothing — Spanish, from the source

The card winning matters twice: a bad English string can be fixed without a
firmware build, and a third language works through exactly the same path as
the second, with no special case.

**What changed**

- `gen_lang.py embed en` writes `components/aos_ui/aos_lang_embedded.c`: one
  `aos_lang_pack_t` per language, one C string literal per catalog line. It
  strips the `#:` reference comments, which are about 60 % of a template file.
  Regenerate it whenever the English pack changes - it is generated source,
  committed like `aos_symbols.c`, not built on the fly.
- It lands **inside `aos_ui`, not in a component of its own**, for the same
  reason `aos_i18n.c` does: aos_ui is already globbed by the firmware build
  and by the simulator, and is already in `gen_symbols.py`'s library list. A
  new component is three hand-written wirings and each one is a place to
  forget something.
- `catalog_load()` falls back to the embedded blob when the file is not there,
  copying it into a `malloc`'d buffer first, because `unescape()` writes in
  place and the blob is const in flash.
- `aos_i18n_scan()` appends the embedded languages the card did not already
  provide, deduped by code, so the list shows the pack that will actually load
  rather than both.
- `aos_lang_t` gained `.embedded`, and Settings prints it under the coverage
  line - "357 strings, 18 apps covered / card". On its own line and not
  appended with a bullet: in one line the pseudolocalized version runs from
  x=-7 to x=376 on a 368 px screen, which is exactly what that pack is for.
- `/api/lang` reports it too, as `"origen": "firmware" | "tarjeta"`.

**What it cost.** 22.2 KB in the object file, **19.5 KB on the final image**
(0x275c60 -> 0x27aa70), for 357 system strings and 18 app catalogs. The app
partition still has 50 % free.

**What it does not change:** Spanish stays the source language and needs no
catalog; `aos_tr()` still returns its argument when nothing matches; the pack
format, the tools and the four verifications all stay as they are. The English
pack on the card is now redundant, but harmless - and it is still the way to
fix a bad string without a firmware build.

## The first app born multilingual (2026-09-06)

Everything above describes retrofitting: 27 firmware files and 19 apps written
in Spanish and wrapped afterwards. `cjump` (Claude Jump) is the first app
written with `_()` from its first line, and it is worth writing down what that
changed, because most of it is not what the phases predicted.

**Almost nothing changed.** Wrapping as you go costs nothing - the marker is
three characters - and the `template` / `check` / `unmarked` circuit worked on
the first run: 45 keys extracted, 45 translated into English and German, zero
findings from `unmarked`. There was no separate translation phase because there
was nothing to go back and find.

**What did change is a design decision taken up front.** The three apps that
draw with their own 5x7 bitmap font - 2043, arkanos, claudito - have
transliterated catalogs, because those fonts have no accents and
`gen_lang.py check` enforces ASCII on them. That constraint is permanent and it
shows on screen: *DANKE FUERS SPIELEN*, not *FÜRS*.

cjump draws with a canvas too, and the same font. It avoids the whole class of
problem by a rule stated in `cjump.h` before any code was written:

> **No translatable text goes through the canvas.**

The scoreboard is numbers plus `M`, which is a unit and not a word. Every word
in the app - menu, shop, pause, game over, the sixteen skin names - is an LVGL
label, so it gets accents, umlauts and eszett for free. The catalog is not in
`check`'s ASCII list and never needs to be.

The cost is that a canvas game cannot put words on the canvas. In practice that
means the HUD carries an icon where another game would carry a word: a little
coin instead of *monedas*. That is a better HUD anyway.

**One thing the retrofit habit got wrong.** The first draft wrote the Spanish
without accents - *Record*, *Se acabo*, *Menu*, *Todavia no alcanza* - out of
the reflex that comes from the canvas-font apps. The keys are the Spanish
strings, so that would have shipped bad Spanish forever and orphaned the
catalogs the day someone fixed it. Caught by reading the generated template,
which is the one artifact that shows every user-visible string of an app in one
place. Worth doing once per app.

## Known traps

- **Text length.** The layout was built against Spanish on a 368 px screen.
  English shrinks, so the first language is easy; German and French grow.
  `lv_obj_align_to()` computes its position once and does not recompute when
  the object resizes, which is why `aos_label_boxed` exists. Every new language
  is a QA pass over ~40 screens.
- **Partial packs.** A pack covering the firmware but not the apps leaves a
  mixed UI. Treat it as normal and visible - `meta.txt` declares coverage and
  Settings shows "system and 6 of 19 apps".
- **`.rodata` pointers in a `.so`.** Every `_()` in an app is a literal in the
  app's `.rodata` plus a pointer, the same shape that used to crash the loader
  through `.data.rel.ro`. That bug is fixed in the local `elf_loader` copy, but
  **this is the first thing to test on hardware**: one app with `_()` and a
  loaded catalog, before wrapping the other eighteen.
- **Things that must not be translated.** The POSIX TZ strings in
  `aos_app_worldclock.c` (`PST8PDT,M3.2.0,M11.1.0`) are configuration. The
  truco calls (`envido`, `quiero retruco`) are the name of the game - leave
  them unwrapped on purpose.
- **`build_apps.sh` gets expensive.** Any change to the chain rebuilds 19 apps
  and re-verifies ABI and symbols.

## F7 - dropping LVGL's own Montserrat (done)

F1 left both font sets compiled in, because turning the stock ones off would
have dropped them from the dynamic-app symbol table and broken the four apps
that named them directly. F5 migrated those four. This removes the duplicate:
**-266.7 KB, from 2.48 MB down to 2.22 MB**, 56 % of the partition free.

Only `aos_montserrat_*` and `lv_font_fmt_txt` (the glyph-format *code*, which is
needed) are left in the map.

### The Kconfig choice fights back

Turning `CONFIG_LV_FONT_MONTSERRAT_14` off by hand does not stick. The theme's
default-font list is a Kconfig `choice` whose every entry **`select`s** the font
it names, so as long as "Montserrat 14" is the theme font, Kconfig turns the
font back on underneath you. The list offers no custom entry - only LVGL's own
fonts.

The way out is two moves:

1. Point the choice at **UNSCII 8**, the cheapest option that is not a
   Montserrat. This satisfies Kconfig.
2. Override the result with a `-D`, in
   `components/aos_fonts/aos_fonts.cmake`:

```cmake
idf_build_set_property(COMPILE_DEFINITIONS
    "LV_FONT_CUSTOM_DECLARE=LV_FONT_DECLARE(aos_montserrat_14)" APPEND)
idf_build_set_property(COMPILE_DEFINITIONS
    "LV_FONT_DEFAULT=&aos_montserrat_14" APPEND)
```

`lv_conf_internal.h` tests `#ifndef LV_FONT_DEFAULT` *before* it looks at
`CONFIG_LV_FONT_DEFAULT`, so the `-D` wins. It has to be included **before**
`project()` in the root `CMakeLists.txt`; after that the component flags are
already fixed.

A default font is not optional: it is the `.ptr` of the `text_font` entry in
`lv_style.c`'s default table and what `lv_theme_get_font_*()` falls back to -
every widget nobody styled explicitly draws with it.

### Exporting a symbol is referencing it

Two fonts survived the first pass and were still in the binary:

| | Size | Why it was there |
| --- | ---: | --- |
| `lv_font_montserrat_14_aligned` | 35.8 KB | a separate Kconfig option, nothing in the project names it |
| `lv_font_unscii_8` | 7.4 KB | the choice above had to pick *some* LVGL font |

Neither is used. Both were in the image **only because `aos_symbols.c` exported
them**, and `ESP_ELFSYM_EXPORT` is a reference: it pulls the object out of the
archive. `gen_symbols.py` already had `SKIP_OBJECTS` for exactly this - it is
why the demos are excluded - so the built-in font families joined that list.
The filter names the families rather than the whole `lv_font_` prefix, because
apps do need `lv_font_get_glyph_dsc()` and friends.

### Verify the `-D` landed as an address, not a string

`-DLV_FONT_DEFAULT=&aos_montserrat_14` reaches the compiler as
`-DLV_FONT_DEFAULT="&aos_montserrat_14"` - shell quoting, because `&` is a
metacharacter. If those quotes ever became part of the macro, `.ptr` would be a
string literal, which **compiles fine** (`.ptr` is `const void *`) and draws
from garbage. Two checks settle it:

```
xtensa-esp-elf-objdump -r .../lv_style.c.obj | grep montserrat
    0000000c R_XTENSA_32       aos_montserrat_14        <- a real relocation
strings build/amoledos.bin | grep -c '&aos_montserrat'
    0                                                    <- no string literal
```

The linker map is not enough here: it lists only the first reference that
pulled an object out of an archive, which was `aos_symbols.c` either way.

### Two things this uncovered

- **`project_so()` does not quote its command line.** The `.so` step builds its
  compiler invocation as a raw string, so the `&` and the parentheses in those
  two `-D`s reach `/bin/sh` and all 19 apps die with *syntax error near
  unexpected token `(`*. The apps do not need them - `LV_FONT_DEFAULT` is used
  only inside LVGL's own `.c` files - so `apps/common.cmake` deliberately does
  not include that file, and says so. Should an app ever need it, it surfaces
  as an undefined symbol and `build_apps.sh` checks every one of those.
- **The simulator had been building LVGL's demos and examples all along.**
  `sim/CMakeLists.txt` set `LV_CONF_BUILD_DISABLE_EXAMPLES`, which
  `os_desktop.cmake` never reads - the real switches are
  `CONFIG_LV_BUILD_EXAMPLES` / `CONFIG_LV_BUILD_DEMOS`, declared with
  `option(... ON)`. Nothing failed, so nobody noticed until
  `lv_example_style_21.c` turned out to be the one file that still named a
  Montserrat. They are off now (with `FORCE`, since `option()` will not
  overwrite an existing cache entry).

### Verified

39 screens x 4 languages: **the audit output is identical to the run before
this change**, line for line. On the board: all 19 `.so` apps load
(`apps dinamicas cargadas: 19`) against the trimmed symbol table.

## Out of scope

- **Arabic and Hebrew.** `LV_USE_BIDI` is off, and enabling it still leaves
  shaping and mirrored layouts. That is a different UI, not another pack.
- **CJK.** Thousands of glyphs cannot be compiled in. `lv_binfont_create()`
  would work today (`LV_USE_FS_POSIX` is on) but loads the font into RAM rather
  than memory-mapped flash, and line breaking differs.
- **`aos_web`.** The config portal has ~100 more literals in HTML with its own
  mechanism. Later, or just honour the browser's `Accept-Language`.
