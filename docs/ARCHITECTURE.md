# Architecture

## The rule that holds everything up

**`aos_ui` and `aos_apps` include only LVGL and `aos_hal.h`** — never an ESP-IDF
header. That is why the same interface code compiles for the board and for the
desktop simulator, and why every screen can be designed, audited and
screenshotted on a Mac.

```
main/                    startup on the board
sim/                     startup on the desktop (SDL2)

components/
  aos_hal/               the single contract with the platform
    aos_hal_esp32.c        board implementation
    aos_http.c             HTTP/TLS client, shared by both platforms
    aos_notif.c            notification store and policy, shared by both
    aos_scan.c             network survey
  aos_board/             AXP2101, PCF85063A, QMI8658, revision detection
  aos_ui/                UI runtime: launcher, watchfaces, navigation, theme,
                         i18n, notification overlay
  aos_apps/              the 18 built-in apps
  aos_dynapp/            .so loader and symbol table
  aos_ble/               NimBLE: ANCS, AMS, pairing (board only)
  aos_web/               the web portal, embedded in the binary (files, wifi,
                         app settings, and the OTA endpoint)
  aos_fonts/             Montserrat with the Latin-1 supplement
  elf_loader/            Espressif's ELF loader (Apache-2.0, vendored)

apps/                    21 dynamic apps, one directory each
tools/                   generators, test benches and board utilities
```

The screen is laid out like this:

```
screen
+-- stage            (368x448, black)
|   +-- watchface    layer 0, always alive
|   +-- launcher     layer 1, created the first time it is used
|   +-- app root     layer 2, one per open or backgrounded app
+-- statusbar        overlaid on top
+-- toast            ephemeral
```

Navigation is by gesture: swipe up from the clock opens the menu, swipe right
goes back. The gesture handler is attached to the **input device**, not to the
screen, because LVGL sends the gesture to the object under the finger and only
bubbles it to parents that carry `LV_OBJ_FLAG_GESTURE_BUBBLE`.

## Two platforms, one HAL

`aos_hal.h` is the whole contract: display, touch, battery, IMU, time,
brightness, buttons, storage, preferences, audio, microphone, recorder, media
control, Bluetooth, notifications, network, HTTP and the network survey.

There are two implementations — `aos_hal_esp32.c` and `sim/hal_sim.c` — and two
files that are shared by both because they contain no platform code at all:

* **`aos_http.c`** — lwIP gives the board the same POSIX sockets macOS gives the
  simulator, and mbedtls 3.x is the same API on both. The only thing that
  differs is where the trusted certificate store comes from, which is one
  function.
* **`aos_notif.c`** — the notification *policy* (do not disturb, category
  filter, the phone's own silence, "calls always", burst grouping). The provider
  differs — ANCS on the board, an imaginary phone in the simulator — but the
  decision is written once and tested on the Mac.

The simulator is not a toy. It runs the real UI runtime, the real apps, the real
policy and the real HTTP client; it fakes the battery, the IMU, the microphone
(it synthesises speech) and the network survey. What it cannot fake is the
board's timing and the touch panel's ceiling, which is why both are documented
in [HARDWARE.md](HARDWARE.md) and checked by the layout audit.

## Dynamic apps

An app is a shared object (`.so`) built separately with ESP-IDF and copied to
`/sdcard/apps`. At startup the firmware walks that directory, `dlopen()`s each
one, checks the ABI version and registers the app in the menu like any other.

The `.so` links against nothing. Its calls into LVGL, the HAL and libc are left
unresolved and the firmware fills them in at load time from a table of **2447
symbols** generated by `tools/gen_symbols.py`.

Two details that are easy to get wrong:

* The entry point is **two functions**, not a structure. Espressif's loader
  builds its symbol index filtering on `STT_FUNC`, so `dlsym()` cannot find a
  data object — an exported structure fails with "does not export
  aos_app_entry" even though `nm` shows it perfectly.
* Apps are loaded **on demand**. At startup each `.so` is opened only far enough
  to read its descriptor and closed again; the code enters RAM when the user
  opens the app. This is not an optimisation, it is the only thing that fits:
  the apps' `.text` has to live in executable internal RAM, of which there is
  about 83 KB, and the apps together are far more than that.

### The memory asymmetry that shapes app design

```
one line of code costs        ~8 bytes of a 48 KB pool
one kilobyte of table costs    nothing (the loader sends .rodata to PSRAM)
```

Every app of any size in this repository is built around that. Chatarra's 64
robot parts are not 64 sprites and not 64 functions: they are 64 *descriptors*
of a handful of bytes plus four drawing functions that interpret them. Its whole
world — maps, dialogue, items, attacks — is `const` tables. Adding a town adds
not one line of code.

## Drawing

This is where most of the measured work went.

### LVGL layers are very expensive

LVGL allocates a **separate layer buffer** for any object *with children* given
opacity or a transformation, and for any rotation or scale. At full screen that
is 322 KB to allocate and clear per frame; when it does not fit, LVGL hangs in
an infinite retry rather than degrading.

So: the press highlight on a button goes by colour, not by `transform_scale`.
The launcher's watchOS-style fade scales only the *icon* (an 8 KB layer instead
of 60 KB) and applies opacity only to the *text*, which LVGL blends inline.
Icons are drawn from cardinal shapes, never rotated ones, because the menu
redraws every visible icon on each frame of a scroll.

### Never let LVGL stretch a canvas

Games draw into a small RGB565 buffer and upscale it **by hand** to 368x448.
Letting LVGL do it with `LV_IMAGE_ALIGN_STRETCH` costs a measured **129 ms per
frame** (7 fps), because `lv_draw_sw_transform` generates a per-pixel alpha
plane for an RGB565 source and composites with blending instead of copying.
Upscaled by hand, the canvas is 1:1 and for LVGL it is a flat copy.

### Dirty rectangles

Arkanos, Claude Jump and Chatarra keep two buffers — `bg` with what stands
still, `fb` with the frame — and per frame:

1. restore from `bg` the rectangles dirtied last frame,
2. draw what moves, each thing recording one rectangle,
3. upscale and invalidate **only** the union of the two sets.

That takes the work from "the whole screen" to a few thousand pixels. It works
for a *scrolling* game too, as long as the background does not scroll: Claude
Jump's sky is fixed in screen coordinates, exactly as the original Doodle Jump's
squared paper is.

The failure mode is specific and worth knowing: anything that moves and does not
record its rectangle leaves a **trail stuck on the screen**. Nothing crashes. It
only appears after a while of playing, which is why `apps/arkanos/tools/ak_harness.c`
draws every frame twice — once by the fast path and once rebuilding from the
background — and compares the two buffers.

### Rebuilding LVGL objects is expensive

Rebuilding a twenty-row list costs **111–124 ms** with the LVGL thread blocked;
filling the same rows in costs 18–31. Clima's hourly strip cost 120 ms per
refresh until its ~80 objects were created once and only their contents changed.

And LVGL does not compare: writing the same text to a label, or the same colour
to a style, invalidates it all the same. Several apps keep the last value
written and only touch the object when it really changed.

### Frames adjust themselves

If a frame comes out more expensive than the timer's period, the timer is always
overdue, the LVGL task never sleeps, CPU 0's idle task never runs and the
task watchdog fires — which on this board leaves the screen frozen. So the games
measure how long a frame really takes and relax the period until it fits, then
tighten it again when there is time to spare. The floor is 33 ms because
`CONFIG_LV_DEF_REFR_PERIOD` is 33: LVGL does not refresh more often even with
CPU to spare.

## Concurrency

LVGL is not thread-safe. Everything that touches an LVGL object either runs on
the LVGL task or takes `aos_hal_lock()`.

Three things arrive from other tasks and are therefore *deferred* rather than
applied where they happen:

* **Notifications** — NimBLE's callback runs on the BLE host task. It pushes
  into a queue; the only place a notification becomes pixels is `aos_ui_tick()`.
* **Screenshots** — `lv_snapshot_take()` walks the object tree and draws it, so
  it has to run on the task that owns LVGL. The HTTP server asks and polls.
* **Language changes** — applying one frees the strings the current screen is
  built from, so it is requested and applied on the next tick.

The same pattern appears inside apps: `aos_ui_back()` destroys the app, so
calling it from an event callback would destroy the object dispatching the
event. Apps note the request and act on the next frame.

## Test benches

Anything that can be verified without the board is, in `tools/`:

| Bench | What it proves |
| --- | --- |
| `qr_harness.c` | the WiFi QR's escaping — a malformed QR draws perfectly |
| `nt_harness.c` | the notification policy's five crossing conditions |
| `ancs_harness.c` | the ANCS protocol, byte for byte, without an iPhone |
| `ams_harness.c` | the Apple Media Service protocol |
| `tx_harness.c` | text sanitising — LVGL draws *nothing* for a missing glyph |
| `af_harness.c` | pitch detection's octave errors and the A-weighting curve |
| `cz_harness.c`, `sn_harness.c` | the JSON/text readers |
| `http_harness.c` | the real HTTP client with and without TLS, including badssl.com |
| `mic_harness.c` | the microphone ring against the simulator's HAL |
| `apps/*/tools/*_harness.c` | per-app: level solvability, dirty rectangles, game rules |

`tools/audit_layout.sh` opens every app in the simulator in every installed
language and reports text that does not fit, runs off screen, overflows its
container, or sits below the touch ceiling. What matters is the *difference*
between languages: a finding that appears identically in both is pre-existing,
not something a translation broke.

It is a sweep and costs minutes: it is for adding a language, touching the
theme or a shared widget, and for release checks. One screen is audited on its
own with `AOS_SIM_AUDIT=<label> AOS_SIM_VIEW=<id>`, which is the same check in
a second.
